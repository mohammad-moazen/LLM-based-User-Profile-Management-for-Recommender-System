# Runtime Repeatability Baseline

## Purpose
This diagnostic measures whether the active local LLM produces stable Review Extractor outputs when the exact same requests are repeated under an unchanged LM Studio runtime profile.

## Runtime profile
- model API identifier: `llama-3.2-3b-instruct-uncensored`
- local model format: GGUF
- quantization observed in LM Studio: `Q8_0`
- context length: 8192
- GPU offload: 28 / max
- CPU thread pool: 7
- evaluation batch size: 512
- physical batch size: 256
- max concurrent predictions: 1
- Unified KV Cache: ON
- KV cache offload to GPU: ON
- Flash Attention: ON
- K/V cache quantization: OFF
- speculative decoding: OFF

Generation settings are supplied by the Python API request, not inferred from the LM Studio Inference UI. The benchmark used `temperature = 0.0`, `seed = 42`, `max_tokens = 512`, and the same evidence-backed JSON schema as the active Review Extractor code.

## Result
The same 12 deterministic tasks were replayed 3 times (36 measured requests total) after 2 warm-up requests.

Latency:
- overall mean: 3.764 s/request
- overall median: 3.331 s/request
- pass means: 3.765 s, 3.764 s, 3.762 s
- standard deviation of pass means: 0.0017 s

Same-profile repeatability:
- exact repeat pairs: 36 / 36
- exact repeat-pair rate: 100%
- mean pairwise Jaccard: 1.000
- median pairwise Jaccard: 1.000
- minimum pairwise Jaccard: 1.000
- every sampled task produced exactly one profile variant across the three passes

Comparison with the historical frozen Phase 3 rows:
- exact match vs historical frozen output: 8 / 12 (66.7%) on every pass
- mean Jaccard vs historical frozen output: 0.7994
- median Jaccard vs historical frozen output: 1.000
- minimum Jaccard vs historical frozen output: 0.1429

Memory across the 36 measured requests:
- private-memory delta: -0.041 GB
- working-set delta: +0.051 GB

## Interpretation
The active current inference path is highly repeatable: all 36 pairwise comparisons between repeated passes were exactly identical. Therefore the earlier 8/12 mismatch against historical Phase 3 output is **not evidence of ongoing random run-to-run variability** under the current profile.

A more plausible explanation is protocol drift between the historical extraction rows and the current final extractor code. In particular, after the first full attempt the blank-evidence fix changed the active prompt/schema behavior (including explicit non-empty evidence requirements), while 131 already-successful historical rows were retained through resume and only 3 failed tasks were regenerated. The historical Phase 3 directory is therefore a valid audit artifact of the development sequence, but it should not be treated as a homogeneous final-protocol output set for thesis-grade downstream evaluation.

## Consequence
Before Profile Updater is frozen, create one clean homogeneous Review Extractor run using the final accepted prompt/schema/validator and one finalized runtime profile. The historical 134/134 result remains preserved; it is not overwritten.

For runtime tuning, comparisons should use a fresh reference generated by the **current final extractor code** under `512 / 256 / concurrency 1`, then compare faster loader profiles against that reference. This avoids confounding runtime changes with historical prompt/schema drift.
